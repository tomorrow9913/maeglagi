# Meeting review and workspace directory API

All routes are under `/api/v1/workspaces/{workspaceId}` and use the existing bearer auth. Every resource lookup is scoped to the authenticated workspace owner; an ID from another workspace or owner returns `404`. JSON request and response fields use camelCase. Directory people are meeting participants, never account members or access grants.

## Directory

- `GET /people` lists active and archived people. `POST /people` accepts `{name, role?: string|null, aliases?: string[]}` and returns `201 {id, workspaceId, name, role, aliases, archivedAt, createdAt, updatedAt}`. `PATCH /people/{personId}` accepts `{name?, role?, aliases?, archived?}` and returns the same shape. Names are 1–120 characters; role is optional and at most 120 characters; aliases are deduplicated, 1–120 characters each. Role describes a participant's work, not an application permission.
- `GET /projects` lists active and archived projects. `POST /projects` accepts `{name, goal?: string|null, description?: string|null, ownerPersonId?: uuid|null, startsOn?: date|null, endsOn?: date|null}` and returns `201 {id, workspaceId, name, goal, description, ownerPersonId, startsOn, endsOn, archivedAt, createdAt, updatedAt}`. `PATCH /projects/{projectId}` accepts those fields plus `archived?` and returns the same shape. Names are 1–120 characters; optional text is at most 4000 characters; dates use `YYYY-MM-DD` and end must not precede start. `ownerPersonId` must identify an active person in this workspace.
- Archive is reversible. No hard-delete endpoint is exposed; archived records remain available in confirmed source snapshots.

## Meeting review

- `POST /sources/recordings` still accepts multipart `audio`. It may also accept `projectId` as a UUID form field and `liveDraft` as a JSON string with `{utterances: [{id, personId?: uuid|null, speakerName, text, startSeconds?: number|null, endSeconds?: number|null}]}`. The response remains a `202` job. Audio upload enqueues only transcription. A valid live draft is retained as the editable review draft; server STT is stored separately and does not overwrite it.
- `POST /sources/transcripts` accepts `{title?, text, durationSeconds?, projectId?: uuid|null, utterances?: [...]}` and creates an `awaiting_review` draft without indexing or analysis. If `utterances` is omitted, the text becomes one editable utterance. The response uses the existing job shape with `status: "awaiting_review"` and `stage: "awaiting_review"`. Both upload forms validate the optional project against active projects in the owner workspace and persist it immediately, so a refresh retains the capture selection.
- `GET /sources/{sourceId}/review` returns `{sourceId, title, transcriptSource, reviewState, status, stage, errorMessage, revision, projectId, utterances, rawTranscriptText, rawUtterances, confirmedAt, confirmedSnapshot}`. `reviewState` is `transcribing`, `awaiting_review`, or `confirmed`; `status`, `stage`, and `errorMessage` match the job payload so a terminal STT failure can stop polling and show retry. `confirmedSnapshot` is null until confirmation. `rawTranscriptText` and `rawUtterances` preserve server STT independently of edits.
- `POST /sources/{sourceId}/review/retry-transcription` has no body and returns `202` with the existing job payload. It accepts only an owner-scoped server recording in `reviewState: "transcribing"` and `status: "failed"`, then queues STT using the same stored audio and source ID. A repeated call while queued or processing returns the current job without another publication; awaiting review or confirmed meetings return `409`. An existing `liveDraft` is retained through the retry, and no downstream indexing or analysis runs until confirmation.
- `PATCH /sources/{sourceId}/review` accepts `{revision, projectId: uuid|null, utterances: [...]}` and returns the updated review payload with `revision + 1`. It is allowed only while `awaiting_review`. IDs are stable, unique strings; text and speaker names are trimmed; blank utterances may be saved for later editing. The project and any person IDs must be active and owned by the same workspace. A stale revision returns `409` with no write.
- `POST /sources/{sourceId}/review/confirm` accepts `{revision}` and returns `202` with the existing job shape. It requires an active selected project, at least one nonblank utterance, and valid person references. Confirmation drops blank draft rows, replaces each retained row's display speaker name with its selected person's canonical name, then stores the canonical transcript and an immutable snapshot of the selected project and referenced speakers (including roles and aliases). A person selected only on a blank row is not recorded as an attendee. The project snapshot also includes its owner person's name and role even when that person is not a speaker; it does not claim that person attended. A stale revision returns `409`. Repeating confirmation for the same revision is idempotent: it returns the current job and may retry a failed queue enqueue without changing the confirmed snapshot or revision. Concurrent confirmations serialize on the source row; publication completes before releasing the lock.

New meeting sources never embed or write Context Store, Timeline, or Graph data before confirmation. Worker retries cannot bypass the review state or retranscribe confirmed content. Existing succeeded meeting sources migrate as confirmed and remain readable. A legacy server meeting with saved transcript text migrates to an editable review draft with the raw text retained; one without text remains in transcription. In environments with old ingestion workers, drain them before migration and before enabling new workers so they cannot write downstream during rollout. The new directory tables enable PostgreSQL row level security without client policies; backend owner-scoped endpoints use the backend database role. Documents continue their existing flow.

Worker attempts serialize with a blocking PostgreSQL transaction advisory lock keyed by source ID on a dedicated held connection. Source-write sessions may commit during parsing, STT, indexing, and analysis without releasing that lock; a duplicate or redelivered task waits and then rechecks persisted status. The lock transaction pins a backend connection under transaction pooling and rolls back to release the lock on completion or worker connection loss, so deployment must allow one extra PostgreSQL connection per active ingestion task. Lock/connection failures retry without acknowledging a persisted `processing` source; model processing failures retain their three-attempt limit. Source status and stage are stored in existing text columns and represented in Python by string-compatible enums; no native PostgreSQL enum migration is needed.

## Verification and rollout limits

- Backend: 403 pytest tests passed; Ruff check and format passed. An isolated PostgreSQL 16 migration covered five legacy meeting states. Real SQL concurrency checks returned one successful review save and one `409` for stale revision, and one fake queue publication for simultaneous confirmations. The new advisory lock and STT retry paths have automated state and concurrency tests. A separate isolated PostgreSQL 16 check used the exact lock helper to verify that another connection waits through a source-write commit, then proceeds when the holder finishes or is cancelled; the temporary container was removed.
- Frontend: 17 tests, lint, typecheck, and production build passed. Browser QA covered two projects and a participant with role/alias, project and speaker selection in Ask, Tab to add a transcript row, `awaiting_review` upload, edited draft save, explicit confirmation on the same job, and the corrected source viewer.
- Rollout: the additive migration was applied to the matched production Supabase project after confirming zero existing sources; Alembic revision and row level security readback were verified. The PR and application rollout remain pending. Real microphone capture, paid provider calls, and end-to-end Celery integration were not exercised; the browser walkthrough used the demo API and a fake queue was used in the concurrency check.
